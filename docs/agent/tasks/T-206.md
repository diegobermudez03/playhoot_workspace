# T-206 — Admin web base

**Tier:** B (Opus · medium) · **Size:** L · **Repos:** frontend · **Milestone:** H2 · **Requires:** T-201, T-204 (shell patterns); T-203 if available (otherwise neutral tokens)

## Goal
Build the admin area of D-023 over the H1 endpoints: admin sign-in with the second factor, TOTP enrollment, the admin shell, and the first three panels — queues/DLQ, budget status and email mode. Six screens, all already specified in the site data.

## Read first
- Site data: every screen in `playhoot_frontend/docs/system/screens-admin.js` (the contract), and the invoked endpoints in `playhoot/docs/system/api.js` (their summaries carry the error outcomes).
- `DECISIONS.md` D-011, D-015, D-017, D-018 (how TOTP, step-up, budget and email behave), D-023, V-03, V-05.
- `SPEC_MAP.md` §20; P32§4,§7 and P31§2 for what the budget and email panels must show.
- `STATE.md` note on becoming admin locally (env var + enroll) — the Result must keep those steps working through the UI.
- `playhoot_frontend/AGENTS.md`.

## What to build
1. **Admin area** under `/admin`: its own minimal shell (navigation, who is signed in, sign out of admin mode), desktop-first single responsive implementation per screen (D-023). Not linked from the public shell.
2. **Admin sign-in** (`/admin/sign-in`): account sign-in reusing T-205 pieces, then the 6-digit code (purpose `admin_token`). Handle `not_admin`, `invalid_code`, lockout with Retry-After (V-03). The 15-minute token lives in memory; expiry returns here and then back.
3. **Second factor** (`/admin/second-factor`): enrollment with the secret/otpauth shown once (QR rendered client-side from the URI, no external service), first-code confirmation, replacement with current code, pending-enrollment lapse message (D-015).
4. **Overview** (`/admin`): ladder level, dead tasks per queue, email mode + today, each linking to its panel.
5. **Queues panel**: dead tasks grouped by queue with type, key, attempts, last error, died-at; retry and cancel with `not_dead` treated as success-with-notice; refresh after actions.
6. **Budget panel**: ladder with reason and history; per category and global caps vs measured/estimated/reserved per window; the three sensitive actions (set controls, cutoff, reopen) each with an inline fresh-code confirm step → `POST /v1/identity/totp/verify` (purpose `step_up`) → action with `step_up_proof`; `step_up_required` re-asks. Reopen shows the gradual semantics (first call closes all at restricted; next calls name categories).
7. **Email panel**: mode switch (Automatic / Resend only / SES only), per-provider consumption vs Resend quotas, deliveries by state, estimated cost. No bodies anywhere.
8. Feature state in a new `packages/features/` package (admin), communication through `packages/communication`; backend values never treated as closed lists (new categories/queues must render).
9. Site data: the six screens → `implemented`; validator at 0.

## Acceptance criteria
- `npm run check` passes; validator at 0.
- Walkthrough against the local backend (compose + env per `STATE.md`): enroll → admin token → see queues/budget/email → retry a dead task → set a cap with step-up → switch email mode. Document the walkthrough commands/clicks in the Result.
- An expired admin token mid-panel returns to sign-in and back without losing the panel state that the URL carries.

## WCAG 2.2 AA checks (this task)
- All panels keyboard-operable; tables with proper headers; row actions reachable and labeled.
- The code inputs are labeled single-purpose fields; lockout and `step_up_required` messages are announced (`role="alert"`).
- Destructive confirms (cutoff, cancel task) are real dialogs with focus trap and explicit action naming; focus visible and not obscured throughout.
- Status colors (ladder levels, delivery states) always paired with text.

## Out of scope
Panels of later milestones (users, games, review queue, plans, markets, free limits — the endpoints for the last two exist but their admin UX arrives with H6/H3 reconciliation in H10), alerts, real providers.
