# T-206 — Admin web base

**Tier:** B (Opus · medium) · **Size:** L · **Repos:** frontend · **Milestone:** H2 · **Requires:** T-201, T-204 (shell patterns); T-203 if available (otherwise neutral tokens)

## Goal
Build the admin area of D-023 over the H1 endpoints: admin sign-in with the second factor, TOTP enrollment, the admin shell, and the first three panels — queues/DLQ, budget status and email mode. Six screens, all already specified in the site data.

## Read first
- Site data: every screen in `playhoot_frontend/docs/system/screens-admin.js` (the contract), and the invoked endpoints in `playhoot/docs/system/api.js` (their summaries carry the error outcomes).
- `DECISIONS.md` D-011, D-015, D-017, D-018 (how TOTP, step-up, budget and email behave), D-023, V-03, V-05.
- `SPEC_MAP.md` §20; P32§4,§7 and P31§2 for what the budget and email panels must show.
- `STATE.md` note on becoming admin locally (env var + enroll) — the Result must keep those steps working through the UI.
- `playhoot_frontend/AGENTS.md`.

## What to build
1. **Admin area** under `/admin`: its own minimal shell (navigation, who is signed in, sign out of admin mode), desktop-first single responsive implementation per screen (D-023). Not linked from the public shell.
2. **Admin sign-in** (`/admin/sign-in`): account sign-in reusing T-205 pieces, then the 6-digit code (purpose `admin_token`). Handle `not_admin`, `invalid_code`, lockout with Retry-After (V-03). The 15-minute token lives in memory; expiry returns here and then back.
3. **Second factor** (`/admin/second-factor`): enrollment with the secret/otpauth shown once (QR rendered client-side from the URI, no external service), first-code confirmation, replacement with current code, pending-enrollment lapse message (D-015).
4. **Overview** (`/admin`): ladder level, dead tasks per queue, email mode + today, each linking to its panel.
5. **Queues panel**: dead tasks grouped by queue with type, key, attempts, last error, died-at; retry and cancel with `not_dead` treated as success-with-notice; refresh after actions.
6. **Budget panel**: ladder with reason and history; per category and global caps vs measured/estimated/reserved per window; the three sensitive actions (set controls, cutoff, reopen) each with an inline fresh-code confirm step → `POST /v1/identity/totp/verify` (purpose `step_up`) → action with `step_up_proof`; `step_up_required` re-asks. Reopen shows the gradual semantics (first call closes all at restricted; next calls name categories).
7. **Email panel**: mode switch (Automatic / Resend only / SES only), per-provider consumption vs Resend quotas, deliveries by state, estimated cost. No bodies anywhere.
8. Feature state in a new `packages/features/` package (admin), communication through `packages/communication`; backend values never treated as closed lists (new categories/queues must render).
9. Site data: the six screens → `implemented`; validator at 0.

## Acceptance criteria
- `npm run check` passes; validator at 0.
- Walkthrough against the local backend (compose + env per `STATE.md`): enroll → admin token → see queues/budget/email → retry a dead task → set a cap with step-up → switch email mode. Document the walkthrough commands/clicks in the Result.
- An expired admin token mid-panel returns to sign-in and back without losing the panel state that the URL carries.

## WCAG 2.2 AA checks (this task)
- All panels keyboard-operable; tables with proper headers; row actions reachable and labeled.
- The code inputs are labeled single-purpose fields; lockout and `step_up_required` messages are announced (`role="alert"`).
- Destructive confirms (cutoff, cancel task) are real dialogs with focus trap and explicit action naming; focus visible and not obscured throughout.
- Status colors (ladder levels, delivery states) always paired with text.

## Out of scope
Panels of later milestones (users, games, review queue, plans, markets, free limits — the endpoints for the last two exist but their admin UX arrives with H6/H3 reconciliation in H10), alerts, real providers.

## Result

Done, 16 Nov 2026. Six screens, one feature package, two clients, one new decision (**D-031**).

### What was built

- **`packages/protocol/src/http/secondFactor.ts` and `admin.ts`** — the paths, request shapes and
  response schemas of the three TOTP endpoints and the three panels, plus the error codes each one
  answers with. Nothing here is a closed list except what the backend itself fixes (the purposes,
  the email modes and quotas, the windows it measures).
- **`packages/communication/secondFactorClient.ts` and `adminClient.ts`** — the two clients. They
  are separate because they are called with different credentials: the TOTP endpoints with the
  account's, everything under `/admin/v1` with the admin-mode token alone.
- **`packages/features/admin` (`@playhoot/feature-admin`)** — `adminSession` (the token in memory),
  `adminSignIn`, `enrollment`, `withStepUp`, `queuesPanel`, `budgetPanel`, `emailPanel`, one
  `adminFailure` reading of every HTTP failure, and the QR encoder.
- **`apps/web/src/features/admin/`** — the admin frame and shell, the guard, the six screens and
  the shared confirm form. Routes added to `src/routes.ts`; `AppShell` already framed `/admin` as
  `plain` from the address (T-204), so no admin page ever shows the public bar.
- **i18n** — 172 new messages in the three catalogs (`es`, `en`, `pt-BR`), including the new
  authentication reason `admin`. The admin area is translated like every other screen.
- **`CodeInput`** gained `autoComplete` and `inputMode`, so a one-time code field is a labelled
  single-purpose field (WCAG 2.2 1.3.5) and a phone shows the number pad.
- **`apps/web/vite.config.ts`** now proxies `/admin/v1` to the backend in development. Only that
  prefix: `/admin` itself is a page of this app.

### D-031, in one line

Admin mode is a **second credential**, not a stronger one: its token lives in a closure, its own
`HttpClient` is the only caller of `/admin/v1`, and when it lapses or is refused the person goes to
`/admin/sign-in?next=<this panel>` and comes straight back. Details and the rest of the decision are
in `DECISIONS.md`.

### Two defects in the site data, fixed here

Implementation tasks build what the site data says; where it could not be built as designed, the
data was wrong and was corrected in the same work (METHOD §7, the task's own rule):

1. **`admin-queues` promised an idempotency key per dead task.** `GET /admin/v1/queues/dead` does
   not answer one — `txqueue.DeadTask` carries domain, uuid, type, payload, attempts, last error,
   admin retries, created-at and died-at. The screen now lists the **task id** and the admin
   retries, and says that cancelling is what frees the key.
2. **`admin-budget` promised the ladder's history.** `GET /admin/v1/budget` answers the current
   ladder row only (level, paused categories, categories a reopening holds closed, reason, actor,
   since). The screen now describes exactly that. A history view would need a new endpoint over
   Budget's append-only change table; it is not worth one in H2 and nothing in P32§7 asks for it on
   screen, so it is simply not promised.

`admin-sign-in` was also corrected: it no longer lists the provider endpoints, because after T-205
there is one authentication screen and the admin sign-in sends people to it rather than drawing its
own provider buttons.

### Walkthrough against the local backend

`docker compose up -d postgres` was already running. The creator's own `playhoot` database still
does not migrate (`CREATOR_TODO.md` P-16), so the walkthrough reused the scratch database T-205 left:

```
cd playhoot
DATABASE_NAME=playhoot_t205 GAME_TOOLCHAIN_DIR=../playhoot_frontend go run .
cd playhoot_frontend
npm run dev -w @playhoot/web -- --port 5174     # 5173 was busy; the proxy sends /v1 and /admin/v1 to :8081
```

Headless Chrome over the DevTools protocol, English (`Accept-Language`). Every step below is a
click or a typed value in the real UI; the TOTP codes were produced by a throwaway RFC 6238 script
from the secret the enrollment screen showed.

| 4 | Read the account UUID, set `IDENTITY_ADMIN_USER_UUID`, restart | `administrator grant for IDENTITY_ADMIN_USER_UUID: created` |

| 7 | Fresh code → "Enter admin mode" | `/admin`: ladder **Normal**, 0 dead tasks, email **Automatic**, "Admin mode ends in 15 minutes" |
| 8 | Queues panel (two dead tasks inserted as fixtures) | Grouped by `notifications`, with type, task id, attempts, last error, died-at |
| 9 | "Retry t206-walkthrough" | "The task is back to pending."; the list refreshed to one task |
| 10 | "Cancel t206-walkthrough" | A real `<dialog>` (open, focus inside it) → "The task is cancelled."; empty state |
| 11 | Budget panel | Ladder, the three figures, consumption per window (a scope with no cap reads **"No cap — blocked"**), caps and prices in force |

Afterwards the scratch database was put back: the remaining categories reopened (nothing held
closed; the ladder de-escalates below shutdown on its own, D-012) and the email mode set back to
Automatic. The fixture dead tasks were deleted; `notifications_queue_tasks` holds only its hourly
periodic task.

**Accessibility pass on the same session** (queues panel, the busiest one): the table has a caption,
six column headers all `scope="col"` and a row header per task; tab order is skip-link → brand →
the five nav entries → leave admin mode → refresh → each row's retry and cancel, in reading order;
the system's single ink focus ring applies (the admin stylesheet declares no `outline` of its own);
one `role="status"` live region per panel plus `role="alert"` on every code field's message; status
colours are always beside their text (ladder levels, delivery states, the mark Status draws). At
390 / 768 / 1280 px there is no horizontal page scroll and the navigation stays visible.

### Not verified here

- The QR is verified by **reading the symbol back** in a unit test — the format bits are checked
  against the eight level-M strings the standard fixes, the mask is read from them, the placement is
  walked in reverse, and every block's Reed-Solomon syndromes must be zero — but **no real phone
  camera has scanned one**. The secret is shown as text beside it, so an enrollment never depends on
  the picture; a scan is worth a minute of the creator's time when they first enroll.
- `step_up_required` from the backend (a proof refused at the action rather than at the code) is
  covered by a unit test, not by the live walkthrough: forcing it needs a proof spent in between.
- Panels of later milestones, alerts and real providers stay out of scope as the brief says.
