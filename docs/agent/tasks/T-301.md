# T-301 — Identity ways in: email code, method linking, recovery

**Tier:** B (Opus · medium) · **Size:** L · **Repos:** backend · **Milestone:** H3 · **Requires:** H2 closed

## Goal
Build the one-time email code as a real way in (P03§8) and method linking and removal (P03§11-12),
exactly as the site data describes them. After this task a person can register or sign in with
nothing but an email address, a guest can upgrade that way, and an account can add or remove ways
in from endpoints the profile will call.

## Read first
- Site data: `identity.email-login`, `identity.link-method`, `identity.list-methods`,
  `identity.remove-method`, the `identity_email_codes` and `identity_email_code_events` tables, the
  changed `identity_external_identities` and `identity.read-contact`, the `email-code-sign-in` flow,
  and the new `/v1/identity/login/email/*` and `/v1/identity/me/methods/*` endpoints
  (`playhoot/docs/system/identity.js`, `flows.js`, `api.js`).
- `DECISIONS.md` D-033, D-035, V-09; P03 §8, §10-12 in full (`docs/definitivos/md/post_03_…`).
- `playhoot/AGENTS.md`; the existing `identity/workflows/accountlogin` (the shape to mirror) and
  `orchestrator/notificationdelivery` + D-018 (the notify path the code email rides).

## What to build
1. **Tables**: `identity_email_codes` + `identity_email_code_events` in identity's migrations
   (edited in place pre-launch, METHOD §6 — tell the creator if the local DB must be recreated;
   new tables alone need nothing). Add `removed_at` to `identity_external_identities` and turn its
   UNIQUE (issuer, subject) partial while not removed.
2. **`identity/workflows/emaillogin`**: StartEmailLogin (normalize, V-09 limits, supersede the live
   attempt, enqueue the `notify` task — type `access-code`, recipient the attempt uuid, keyed by
   it, skeleton carrying the code) and CompleteEmailLogin (hash check, 5-wrong-codes exhaustion,
   resolution identical to the provider callback: existing user / guest upgrade / new account,
   ending a replaced guest session in the same transaction). The code is generated once, hashed,
   and never logged.
3. **`identity.read-contact`** resolves the new recipient form (attempt uuid → address + requested
   language) so `deliver-notification` and `send-notification-email` work unchanged; the entry is
   accepted without a user (notifications: allow an empty recipient for `access-code` only).
4. **Linking**: intent `link` on email attempts (bound account) and on login attempts
   (StartLinkProvider / CompleteLinkProvider — completion links instead of opening a session);
   `method_in_use` when the identity belongs to another user; `ListMethods`; `RemoveMethod` with
   the last-method guard.
5. **Endpoints** as declared in `api.js` (start/complete for sign-in and both link variants, list,
   remove), with their network limits; new operations in identity's catalog at the declared levels.
   Start answers the same acknowledgement whether or not the address exists.
6. Site data for everything this task builds → `implemented`, corrected where building taught
   otherwise; validator at 0.

## Acceptance criteria
- `go build ./... && go vet ./... && go test ./...` green (DB tests against the ephemeral database).
- Table-driven tests cover: register by code, sign in by code, guest upgrade keeps uuid and name,
  wrong/expired/superseded/exhausted codes, enumeration (same answer for known and unknown
  address), link email, link provider, `method_in_use`, remove, last-method guard.
- A live walkthrough against `playhoot_t205` (or a fresh DB): start → the email lands in the
  simulated provider → complete → `GET /v1/identity/me` shows the account; delivery records keep
  no code (P31§5) and the entry's skeleton is cleared once the email is decided.
- Validator at 0; commit and push.

## Out of scope
Frontend (T-304); mode/language/profile reads (T-302); deletion (T-303); real email providers
(delivery 2).

## Result
**Done, 16-nov-2026.** A person can now register or sign in with nothing but an email address, a
guest can upgrade that way, and an account can add or remove ways in.

- **Identity**: `identity_email_codes` and `identity_email_code_events` (new migration);
  `identity/internal/business/emailcode` (normalization, the six digits, the hash, V-09's
  lifetimes and limits); `identity/workflows/emaillogin` (start, complete, and the email link
  steps); provider linking added to `identity/workflows/accountlogin`;
  `identity/usecases/signinmethods` (list, remove, last-method guard). `identity.read-contact`
  resolves an attempt identifier to its address and requested language.
- **Notifications**: a type may now name a recipient that is not a user (`ExternalRecipient`, the
  access code alone): the entry keeps no user, the email task still names the attempt. Nothing else
  in the delivery path changed.
- **API**: the eight endpoints `api.js` declares, with the client-address limits of V-09; the new
  operation `MANAGE_SIGN_IN_METHODS` at account level.
- **Corrections to the design** (all in D-039): `identity_login_attempts` gained `intent` and
  `link_user_id`; exhaustion is derived from the events, not a column; a method is named by its row
  identifier; `notifications_entries.user_uuid` became nullable; the metric series guard rose to
  4000, which the eight new endpoints pushed the per-route counter past.

**Checks**: `go build ./... && go vet ./... && go test ./...` green with the database (the full
suite, DB tests included). Table-driven tests cover register, sign in, guest upgrade, wrong,
expired, superseded and exhausted codes, the identical answer for known and unknown addresses, the
identical answer for a refused rate, linking an address and a provider, `method_in_use`, removal
and the last-method guard. Site documentation updated; validator at 0 over 455 entities.

**Live walkthrough** against a fresh `playhoot_t301`: code asked for -> the email reached the
simulated provider -> completion opened the session -> `GET /v1/identity/me` showed the account ->
a second address linked, signed the same account in, and the first one was then removable. The
delivery records mention no code and the entry's skeleton was cleared once the email was decided.
The code was recovered for the walkthrough by hashing the million candidates against the stored
hash, since it exists nowhere but in the email.

**The creator must recreate their local databases**: migrations were edited in place
(`identity_external_identities.removed_at` and its partial unique index,
`identity_login_attempts.intent` and `link_user_id`, `notifications_entries.user_uuid` nullable).
`playhoot_t205` is stale for the same reason; `playhoot_t301` is fresh and usable.
