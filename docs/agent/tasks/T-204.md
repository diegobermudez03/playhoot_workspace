# T-204 — App shell and public home

**Tier:** B (Opus · medium) · **Size:** M · **Repos:** frontend · **Milestone:** H2 · **Requires:** T-201; T-203 if C-03 is answered (otherwise build on neutral token values per D-021)

## Goal
Build the `app-shell` and `home` screens of the site data: the fixed top bar with mode switch and language, and the public entry that replaces the root redirect. P14§1 is the governing rule.

## Read first
- Site data: `app-shell` and `home` in `playhoot_frontend/docs/system/screens-shell.js` (the contract this task implements), plus the existing `enter-code`/`root-redirect` entries it supersedes.
- P14 §1 and §3 in full (`docs/definitivos/md/post_14_…`); `SPEC_MAP.md` §19.
- `DECISIONS.md` D-019, D-021, D-022; C-01 (guests), C-03 state.
- `playhoot_frontend/AGENTS.md` (two implementations per screen; layers; i18n).

## What to build
1. **App shell** (layout route from T-201's root): fixed top bar with logo/home, join, create, notifications badge with a plain opening panel (`GET /v1/notifications` for the unread count and the entry list; `POST /v1/notifications/{entryUUID}/read` when one is opened or explicitly marked — opening the panel marks nothing, P14§4; a richer notifications page comes with its milestone), profile/sign-up call to action, the 3-mode switch (teacher and student targets show the "arrives with H8" explanation panel when picked, since their modes do not exist yet), and the language selector per D-022. Identity comes from `GET /v1/identity/me` through feature state.
2. **Home** (`/:locale/`): hero explanation, join-code input (goes to the existing join flow), visible accesses to create and to the teacher presentation placeholder, a curated "what Playhoot is" / sample-games section marked clearly as curated until H4's Discovery, and the teacher band. Server-rendered with metadata and JSON-LD per T-201's convention.
3. Replace `root-redirect`: `/` now locale-redirects to home; `/join` remains the join entry reachable from home and the bar.
4. Both screens in horizontal and vertical implementations sharing components.
5. Site data: move `app-shell` and `home` to `implemented`, retire `root-redirect` (delete the entry and its references), keep the validator at 0.

## Acceptance criteria
- `npm run check` passes; validator at 0.
- Home renders server-side with content and metadata (curl check per locale).
- The shell persists across navigation without re-mounting; the unread badge updates on navigation.
- Language change re-renders in place, persists across reloads, and sets `lang`.

## WCAG 2.2 AA checks (this task)
- Top bar fully keyboard-operable; skip-to-content link; focus order logical in both orientations.
- The mode switch and language selector are proper widgets (roles, labels, arrow-key behavior) with visible focus.
- Join-code input has a visible label and autocomplete off; errors are announced.
- Contrast per tokens; nothing conveyed by color alone; bar usable at 320 px width and 400 % zoom.

## Out of scope
Real Discovery (H4), teacher presentation content (H8), notifications list redesign beyond the plain entry list, profile screens (H3).

## Result

**Done 2026-11-16.** The shell and the public home exist, `app-shell` and `home` are `implemented`
in the site data, `root-redirect` is retired, the validator is at 0 (417 entities) and
`npm run check` passes.

### The shell moved above the router (D-028)

Every screen used to render its own `AppShell`, so each navigation rebuilt the bar; and the app's
services lived inside `ClientLayout`, so a server-rendered public page had no identity, no bell
and no sound at all. Both moved into `root.tsx`: one `AppShell` around the `Outlet`, and a
`ServicesBoundary` that hands one set of services to every page once it is interactive. A screen
now says only how it wants to be framed (`useShellMode`: `normal`, `bare`, `immersive`, `plain`),
and the seventeen screens that wrapped themselves were unwrapped. The admin area is recognised
from the address, so T-206 gets no public bar on its pages even for the first render.

### The bar

`app/shell/`: `ShellBar`, `NotificationsBell`, `ModeChoice`, `ShellMenu`. Logo home, join, create,
the 3-mode switch, the bell, the language, the sound, the account corner, and a menu that holds
the install offer (moved out of the bar, T-202) plus whatever the width cannot hold. What shows at
a given width is CSS, not JavaScript, because the bar is server-rendered before anything is known
about the display: below 360 px the mode switch moves into the menu, below 760 px join, create,
language and sound do. The menu disappears when the install offer is the only thing left in it and
the browser cannot install.

The teacher and student modes do not exist yet, so choosing one opens a panel that says what it
will be and leaves the person on the normal mode — it is not a dead control and not a lie.

### Notifications

New layers, one per level: `protocol/http/notifications.ts`, `communication/notificationsClient.ts`
and the feature package `@playhoot/feature-notifications`. The feature state is app-global, like
the credential, because the bar outlives every route; `startServices` follows who is signed in and
reads the list for them or forgets it when they leave. The panel is the plain entry list the task
asked for: unread marked by a dot **and** by the word, the day in the reader's own format and time
zone, and a "mark as read" button. Opening the panel marks nothing (P14§4). A type the backend
sends that this build does not know is still shown, as a notification without a sentence of its
own — the list of types is the backend's and may grow.

### Home

`features/home/HomeScreen.tsx`, two implementations sharing their pieces. Hero with the
explanation, the mascot and the join code with a visible label; create and "teach with Playhoot";
three points on what Playhoot is; the catalog section; the teacher band. Server-rendered with its
metadata, hreflang and JSON-LD, written out at build time.

The catalog section is the one place where this screen could have lied, and D-029 says what it
does instead: it shows **kinds of game**, labelled as our own selection, and says plainly that the
catalog arrives with Discovery and that no activity figures are shown because there are none
(P14§2). No invented game, author or number.

### Two things the task's own data had wrong, and one bug it surfaced

- **`GET /v1/identity/me` per page.** The site data had the shell resolving identity with it. Who
  the person is is already the credential the backend issued and the app renews against it, so a
  call on every page would add nothing and cost a request per navigation. The shell reads identity
  from that state, and the site data now says so (D-028).
- **`enter-code` is still the join page.** The site data had the bar's "join" going to `home`; it
  goes to `/{language}/join`, which exists and is where a code is typed. Corrected in the data.
- **`Mascot` broke hydration.** It gave each instance a blink delay from `Math.random()`, which the
  server and the browser could not agree on. Nobody saw it until T-204 put a mascot on a
  server-rendered page. It now derives the delay from its React id. (Found in the browser, not by
  a test: there is no DOM test environment in this repo.)

### Core components touched

`CodeInput` gained `labelVisible` (the home page shows its code field's label; the join screen
still names it for screen readers only), and `ModeSwitch` gained `size="sm"` for a control that
shares a line with others. Both, and the home screen in both orientations, are in `/design`.

### Verified in a real browser

Chrome over the DevTools protocol, against the dev server:

- `/en`, `/es`, `/pt` render on the server with their content, title, canonical, hreflang,
  Open Graph and JSON-LD, each in its own language (curl, no JavaScript).
- The bar is **the same DOM element** after a navigation (marked it, navigated, it was still
  there), and `GET /v1/notifications` runs on each navigation.
- Changing the language re-renders in place, sets `<html lang>`, writes the cookie and survives a
  reload on an app route.
- Tab order from the top: skip link → logo → join → create → the three modes → language → sound
  → account. Every one of them shows the 3 px ink ring.
- 320 px: no horizontal scroll, every visible bar control at least 24 px, the rest in the menu.
  360, 390, 768 and 1280 px checked the same way. 400 % zoom at 1280 px is the 320 px case.
- The bell: nothing while signed out and no call; "Notifications, 2 unread" once signed in;
  opening the panel sends no read; marking one entry drops the count to 1 and posts to
  `/v1/notifications/{uuid}/read`; an unknown type still listed.
- No console error or hydration warning on `/en`, `/es`, `/pt`, `/en/join` or `/design`.

The bell was driven against **stubbed answers** for its three endpoints, not a live backend: the
backend cannot start on this machine, because its seed inserts Games without `logo_image_url`,
which a later migration made NOT NULL. That is a backend defect, recorded in `GAPS.md` for the
next backend task; it is not frontend work and T-204 did not touch it. Everything else above is
the real app in a real browser.

### Left for later, on purpose

Where a notification leads (P14§6) needs the screens it leads to; each milestone connects its
own. The notifications page itself, preferences, and the teacher and student modes are theirs.
