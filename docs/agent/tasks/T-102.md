# T-102 — Admin second factor and step-up

**Tier:** B (Opus · medium) · **Size:** M · **Repos:** backend · **Milestone:** H1 · **Requires:** T-101

## Goal
The single phase-1 administrator: admin grant, TOTP enrollment and verification, admin-mode tokens, and the single-use step-up proofs sensitive flows consume.

## Read first
- `playhoot/docs/system/identity.js` (planned tables `identity_admin_grants`, `identity_totp_credentials`, `identity_second_factor_checks`; operations `identity.enroll-totp`, `identity.verify-totp`).
- `DECISIONS.md` D-011 and V-03; SPEC_MAP §20.
- How identity issues tokens today (`identity/` usecases, the operation catalog and levels in `identity.authorize`).

## Deliverables
1. The three tables; the admin grant seeded by migration from an environment-named account (document the variable in `.env.example`; no grant when unset).
2. `identity.enroll-totp` (+ confirm) and `identity.verify-totp` issuing either the admin-mode token or a step-up proof; V-03 lockout; code replay refused; every attempt recorded.
3. A helper the orchestrator uses to consume a step-up proof for a named action (used by T-105's flows).
4. Admin level wired into `identity.authorize` and the operation catalog; the two TOTP endpoints.
5. Docs to `implemented`.

## Acceptance criteria
- Repo checks green; tests cover enrollment, confirmation, wrong codes, lockout, replay, proof single-use and expiry, admin token refused without grant or without TOTP.
- Validator at 0.

## Out of scope
More admins, roles, admin screens (H2/H10). The flows that consume step-up (T-105).
