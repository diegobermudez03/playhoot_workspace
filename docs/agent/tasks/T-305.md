# T-305 — Frontend: profile area, notifications pages, teacher mode

**Tier:** B (Opus · medium) · **Size:** L · **Repos:** frontend · **Milestone:** H3 · **Requires:** T-301…T-303 (endpoints), T-304 (sign-in surfaces it links to)

## Goal
Build the person's own corner and the mode switch behind it: the profile and its subscreens
(methods, legal, deletion), the notifications page and preferences, the teacher presentation, and
the shell changes that door them. The site data is the contract; D-034…D-037 carry the reasoning.

## Read first
- Site data: every screen in `playhoot_frontend/docs/system/screens-account.js`, the changed
  `app-shell` and `home` (`screens-shell.js`).
- `DECISIONS.md` D-034, D-035, D-036, D-037, V-10; P03§9-12; P02§9-11,§15; P14§4; SPEC_MAP §19
  (profile without an account, with CTAs).
- `playhoot_frontend/AGENTS.md`; `@playhoot/feature-notifications` and the bell panel (T-204);
  `useShellMode`, `useLocalePaths`.

## What to build
1. **Feature state** (`packages/features/account` or an extension of what exists): my-data
   (`GET /v1/me`), methods, mode, language, deletion — kinds, never backend text.
2. **`/profile`**: identity, name change with the remaining-changes hint (V-10), language (writes
   the account and the local preference), mode switch, guest expiry note + upgrade offer, CTAs when
   anonymous, sign out, doors to the subscreens. **`/profile/methods`**: list, add email (code
   flow), add provider (round trip via `sign-in-complete`), remove with the last-method guard
   explained. **`/profile/legal`**: declaration shown as declared with the support-correction note;
   the four texts with version, acceptance state and download. **`/profile/delete`**: the D-036
   wording (immediate, 30/90, neutral reference survives), guest upgrade offer above deletion,
   explicit confirmation in the native `Dialog`, lands on home signed out.
3. **`/notifications`** and **`/notifications/preferences`** per their site entries: filters,
   explicit read (P14§4), unknown types still rendered; preference switches, marketing toggle
   recording the acceptance/withdrawal with its text shown first.
4. **`/teacher`**: the honest presentation (D-029 style; D-034), reachable from the shell switch and
   the home teach band. **Shell**: teacher switch calls the mode endpoint and navigates; student
   stays explanatory; account menu gains Profile and sign out; bell panel gains "see all".
5. Two implementations per screen (admin exception does not apply here); titles via `appMeta`;
   messages in es/en/pt in parity; site data → `implemented`; validator at 0.

## Acceptance criteria
- `npm run check` (from PowerShell) green; validator at 0.
- Browser walkthrough against a live backend: change name until the limit refuses with the hint;
  add an email method and sign in with it; remove a method and hit the last-method guard; switch to
  teacher and land on `/teacher` with the mode surviving a reload (remembered on the account, not
  the admin-style closure); toggle marketing and see the acceptance recorded; delete a guest and
  land on home signed out.
- Every address reproduces its screen on a cold load.

## WCAG 2.2 AA checks (this task)
- The profile is a navigable landmark structure (headings per section, one `h1`); switches are real
  buttons/inputs with states announced (`aria-checked`/`aria-pressed`).
- The deletion dialog traps focus, names its consequence, and Cancel is the default action.
- Notification list: read/unread conveyed by more than color; mark-read reachable by keyboard.
- Language and mode changes announce their effect (the page language attribute follows).
- 320/390/1280 px without horizontal scroll on every screen.

## Out of scope
Admin panels (T-306); purchases and history sections beyond naming their milestones (H5/H6);
student mode (H8); backend changes.
