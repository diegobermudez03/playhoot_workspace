# T-400 — H4 design: games, versions, publication and Discovery

**Tier:** A (Fable · high) · **Size:** L · **Repos:** workspace, backend, frontend · **Milestone:** H4 · **Requires:** H1, H2 and H3 closed

## Goal
Design everything H4 builds, and only design it: the game as a product with its card, the split of
versions out of `play/session` into `play/versions` with the four version conditions that must not
be confused, the publication request and its review (the review core of `moderation`), unpublish,
delete and administrative block as three different things, templates with permission and
provenance, categories and tags, public Discovery with search and the public card, "my games", and
the game and creation quotas. Write the design as `planned` documentation data — domains,
operations, flows, endpoints and screens with their calls — and write the implementation tasks
T-401… with the H4 board in `PLAN.md`. Write no application code.

Same shape of task as T-200 and T-300; read T-300's Result for what "design as site data" meant
for a milestone that touched both repositories.

## What is known to be missing (from `GAPS.md`, not a complete list)
- **Versions inside `play/session`**: split into `play/versions`; the four conditions (in editing,
  ready and chosen for new sessions, approved for Discovery, pinned in a session) as distinct state.
- **Publication is automatic today**: request, admin review of version + card + assets together,
  and the previously approved combination staying public while an update is reviewed.
- **Version history, returning to a previous one, unpublish, delete**: none exist; single-game
  deletion feeds the same cleanup pattern as account deletion (D-036).
- **Templates**: the copy exists, nobody can mark a game as one; permission, provenance and
  recommended templates are missing.
- **Categories, tags, Discovery, search, public card, my games, quotas**: none exist.
- **Market gates of the adult functions H4 adds** (publish, templates) and a public read of what a
  place asks for, which the declaration screen needs to name the age before it is answered (D-042).

## Result
Done 2026-11-16, one session (Fable · high).

1. **Decisions D-045…D-051 + V-13/V-14.** The four P15§2 conditions get four homes — in editing and
   ready in `play.versions` (the T-401 split), chosen and approved in `game` as version references,
   pinned in `play.session` — and `game.resolve-playable-version` decides which version a Session
   pins: the owner's chosen one, or the offered approved one for everyone else, so the public never
   runs unreviewed content (D-045). Publication is a frozen combination snapshot
   (`game_publications`) reviewed by moderation's new core; card edits never touch the snapshot;
   unpublish is an offering flag that keeps the approval (re-offering unchanged content needs no
   review); unpublish ≠ delete ≠ block, with the block a recorded moderation measure game executes
   (D-046). Templates are append-only grants recording the permission-text version and the
   asset-rights confirmation, provenance rows feed the credits chain, the featured selection is an
   admin table, and copy-template folds into create-game (D-047). Categories and tags are
   admin-managed vocabularies; search runs over approved snapshots inside game; popularity is
   game's own aggregate fed by play through a new `game-usage` queue delivery type, with honest
   statistic thresholds (D-048, V-13, V-14). `create-game` finally reads `plan.get-user-limits`
   (holding + creations, copies included), and `GET /v1/games` becomes the composed my-games read
   (D-049). The split also moves the build queue onto txqueue and edits migrations in place
   (D-050). Discovery, categories and public cards are server-rendered public routes with a dynamic
   sitemap section, and `compliance.read-place-requirements` closes the D-042 gap so the
   declaration screen can name the age (D-051).

2. **Planned site data loaded, validator at 0 (532 entities, +76).** Backend: 15 new game tables
   (publications and their snapshot tags, offering changes, blocks, taxonomy ×4, template grants,
   provenances, featured, usage days, version choices), 2 tables re-homed under `play.versions`,
   moderation's 3 tables; ~20 new operations across game, moderation, play.versions, play.session
   and compliance; the flows finalize-version, switch-current-version, request-publication,
   review-publication, withdraw-game, block-game, enable-template, browse-discovery,
   view-game-card, my-games, list-game-versions, ingest-game-usage and review-queue detailed;
   create-game and create-session re-stepped; publish-game and `POST /v1/games/{g}/publish` marked
   retired; edit-public-card and copy-template removed (absorbed); 24 new endpoints. Frontend:
   `screens-discovery.js` (discovery, category, public card), the reshaped my-games / create-game /
   workspace-publish, the new workspace-versions, 4 admin panels, and the planned changes to home
   and the declaration screen.

3. **Tasks T-401…T-408 and the H4 board in `PLAN.md`**: versions split → publication and review →
   Discovery catalog → templates and quotas → public Discovery frontend → my games and workspace →
   admin panels (C) → close. Both frontend briefs list their WCAG 2.2 AA checks. 9 sessions against
   the 10–12 estimate.

4. **GAPS updated**: every "Games, versions and publication" row assigned to its T-40x or named
   milestone; the cross-cutting builds-queue and create-game-limits rows now point at T-401/T-404;
   the Frontend rows at T-405/T-406; the declaration-age and public-read rows at T-403/T-406.
   `CREATOR_TODO.md` P-23 now includes the template-permission text.

Scope notes, deliberate: no code; screenshots and description images stay owner-uploaded until H7's

and the creator can veto it like any default.
