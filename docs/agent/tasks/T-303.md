# T-303 — Deletion and guest expiry

**Tier:** B (Opus · medium) · **Size:** M · **Repos:** backend · **Milestone:** H3 · **Requires:** T-301 (methods removal is reused), T-302 helpful

## Goal
Build the one deletion pipeline of D-036: a person deletes their guest or account and access ends
at once, the queued cleanup clears what identifies them across the domains that exist, shared
history keeps working under a neutral reference, and inactive guests expire into the same pipeline
after 90 days. P02§9-11 governs.

## Read first
- Site data: `identity.delete-user`, `identity.expire-guests`, the changed `identity_users` /
  `identity_sessions` / `identity.refresh`, `game.delete-user-games`,
  `play.session.anonymize-user`, `notifications.delete-user-entries`, the `delete-account` and
  `expire-guests` flows, and `POST /v1/identity/me/delete`.
- `DECISIONS.md` D-036, V-11, V-12; P02 §9-11 and §15 in full (`docs/definitivos/md/post_02_…`).
- `playhoot/AGENTS.md`; `utils/txqueue` (D-014) — the cleanup is one idempotent task on the
  identity queue, carried by an orchestrator-registered handler like the delivery types.

## What to build
1. **`identity.delete-user`**: one transaction — sessions deactivated, methods removed, resource
   links and grants revoked, display name cleared, `deleted_at` set — then the `account-cleanup`
   task (idempotency key = user uuid). Identity reads of a deleted uuid answer the neutral deleted
   fact (no name); idempotent.
2. **The cleanup handler** (orchestrator, `delete-account` flow steps 2–4): `game.delete-user-games`
   (first writer of `games.deleted_at`; owned games disappear from reads, existing Sessions
   untouched — P04§6), `play.session.anonymize-user` (clear roster display-name snapshots; rows and
   participant ids stay), `notifications.delete-user-entries` (entries and preferences; suppressions
   stay). Each step idempotent; a dead task is an admin alert in the log and the DLQ (V-12).
3. **Activity and expiry**: `last_used_at` on `identity_sessions`, written by refresh at most once
   per day; `identity.expire-guests` daily periodic task (guests = users with no account row;
   inactivity from newest session use; batches of 500; each expired guest goes through
   `delete-user` with origin expiry).
4. **Endpoint** `POST /v1/identity/me/delete` (guest level): the caller deletes themself; nothing
   here deletes anyone else (admin measures are H9/H10).
5. Site data → `implemented` (flow steps included), corrected where building taught otherwise;
   validator at 0. `TestH1Walkthrough` stays green.

## Acceptance criteria
- `go build ./... && go vet ./... && go test ./...` green.
- Tests cover: delete an account (sessions die in the same transaction, token refused afterwards),
  delete a guest, idempotent re-delete, cleanup task end to end against the DB (games deleted,
  snapshots cleared and still distinguishable per participant id, entries gone, suppressions kept),
  compliance rows untouched, guest expiry picks only 90-day-inactive guests and never an upgraded
  one, `last_used_at` written at most once per day.
- A live check: create a guest, play nothing, delete it, and a Session roster it appeared in shows
  the cleared snapshot while the Session itself still reads.
- Validator at 0; commit and push.
