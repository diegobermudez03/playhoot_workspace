# T-303 — Deletion and guest expiry

**Tier:** B (Opus · medium) · **Size:** M · **Repos:** backend · **Milestone:** H3 · **Requires:** T-301 (methods removal is reused), T-302 helpful

## Goal
Build the one deletion pipeline of D-036: a person deletes their guest or account and access ends
at once, the queued cleanup clears what identifies them across the domains that exist, shared
history keeps working under a neutral reference, and inactive guests expire into the same pipeline
after 90 days. P02§9-11 governs.

## Read first
- Site data: `identity.delete-user`, `identity.expire-guests`, the changed `identity_users` /
  `identity_sessions` / `identity.refresh`, `game.delete-user-games`,
  `play.session.anonymize-user`, `notifications.delete-user-entries`, the `delete-account` and
  `expire-guests` flows, and `POST /v1/identity/me/delete`.
- `DECISIONS.md` D-036, V-11, V-12; P02 §9-11 and §15 in full (`docs/definitivos/md/post_02_…`).
- `playhoot/AGENTS.md`; `utils/txqueue` (D-014) — the cleanup is one idempotent task on the
  identity queue, carried by an orchestrator-registered handler like the delivery types.

## What to build
1. **`identity.delete-user`**: one transaction — sessions deactivated, methods removed, resource
   links and grants revoked, display name cleared, `deleted_at` set — then the `account-cleanup`
   task (idempotency key = user uuid). Identity reads of a deleted uuid answer the neutral deleted
   fact (no name); idempotent.
2. **The cleanup handler** (orchestrator, `delete-account` flow steps 2–4): `game.delete-user-games`
   (first writer of `games.deleted_at`; owned games disappear from reads, existing Sessions
   untouched — P04§6), `play.session.anonymize-user` (clear roster display-name snapshots; rows and
   participant ids stay), `notifications.delete-user-entries` (entries and preferences; suppressions
   stay). Each step idempotent; a dead task is an admin alert in the log and the DLQ (V-12).
3. **Activity and expiry**: `last_used_at` on `identity_sessions`, written by refresh at most once
   per day; `identity.expire-guests` daily periodic task (guests = users with no account row;
   inactivity from newest session use; batches of 500; each expired guest goes through
   `delete-user` with origin expiry).
4. **Endpoint** `POST /v1/identity/me/delete` (guest level): the caller deletes themself; nothing
   here deletes anyone else (admin measures are H9/H10).
5. Site data → `implemented` (flow steps included), corrected where building taught otherwise;
   validator at 0. `TestH1Walkthrough` stays green.

## Acceptance criteria
- `go build ./... && go vet ./... && go test ./...` green.
- Tests cover: delete an account (sessions die in the same transaction, token refused afterwards),
  delete a guest, idempotent re-delete, cleanup task end to end against the DB (games deleted,
  snapshots cleared and still distinguishable per participant id, entries gone, suppressions kept),
  compliance rows untouched, guest expiry picks only 90-day-inactive guests and never an upgraded
  one, `last_used_at` written at most once per day.
- A live check: create a guest, play nothing, delete it, and a Session roster it appeared in shows
  the cleared snapshot while the Session itself still reads.
- Validator at 0; commit and push.

## Out of scope
Frontend (T-305); replay content substitution (H5); billing/classroom cleanup steps (H6/H8);
privacy requests and backup-side purging (H11); admin-initiated deletion (H9/H10).

## Result

Done, 16-nov-2026. One deletion pipeline, used by both the person and the timer.

**What was built.** `identity.delete-user` is one transaction: sessions deactivated, methods
removed, resource links and AI connections revoked, single-use grants deleted, display name,
interface language and account mode cleared (each into its own history), `deleted_at` and
`deleted_origin` set, and the `account-cleanup` task enqueued keyed by the user uuid. The account
row stays, so a deleted account is never mistaken for a guest. `account-cleanup` is a new `txqueue`
delivery type carried by `orchestrator/accountcleanup` on Identity's queue, running
`game.delete-user-games`, `play.session.anonymize-user` and `notifications.delete-user-entries` in
order; every step is idempotent and a dead task is already a log alert plus a dead-letter row the
admin panel reads (V-12, nothing new needed). `identity.expire-guests` is a daily periodic task:
guests with no account row whose newest session use — else their creation — is older than 90 days
go through the same deletion with origin `expiry`, in batches of 500. Refresh notes
`identity_sessions.last_used_at` at most once per session per day, and a rotation carries the mark
onto the successor row. `POST /v1/identity/me/delete` (new operation `DELETE_OWN_IDENTITY`, guest
level) deletes the caller and nobody else. `read-profile` answers a deleted uuid with a profile
that names nobody.

**What building corrected**, all in D-041: deletion also had to stop the method rows from naming
the person (address, provider subject and name cleared, plus the name on a guest's creation
request) and to revoke AI connections; `games.deleted_at` and `identity_users.deleted_at` are
write-once records and need no history row, so the designed `game_histories` write was dropped and
a `deleted_origin` cause column added instead; `last_used_at` is an in-place overwrite and is now
a named exception in the data-history standard, beside the Session owner lease;
`notifications_email_deliveries` are deleted with their entries, in the same transaction, because
they point at an entry by row.

**Tests.** Four new integration suites against a real database (delete-user with both kinds of
person, idempotent re-delete, guest expiry including that an upgraded guest never expires, and
one per cleanup step), a handler suite for the endpoint, two refresh unit cases for the daily
activity note, and `walkthrough_h3_deletion_test.go`: one person signs in, leaves a game and a
roster behind, deletes themself, their credential stops renewing in the same breath, the queue
drains and the shared Session still reads with their place in it and no name on it.
`go build ./... && go vet ./... && go test ./...` green with a database, `TestH1Walkthrough`
included. Validator at 0 (456 entities).

**Live check**, against a backend on 8091 over a fresh `playhoot_t303` database: a guest was
created over HTTP, seeded into a finished Session's roster beside another player, and deleted with
`POST /v1/identity/me/delete` → 200. The roster then read `P1` with an empty name and `P2` still
"Beto", the Session itself still read FINISHED, the User resolved as deleted with origin
`requested`, no session of theirs was still active, and the server log showed the queued cleanup
running with `cleanup_rosters_cleared=1`.

**The creator must recreate the local database** (`CREATOR_TODO.md` P-16): identity's core
migration was edited in place again (`identity_users.deleted_at` / `deleted_origin`,
`identity_sessions.last_used_at`, three new indexes), as were the games and play-sessions
migrations (an owner index and a participant index).

**Left out on purpose**, now in `GAPS.md`: the login-attempt and email-code trails keep observed
addresses that are keyed to the attempt rather than to the User (H11's privacy-request design);
replay content substitution is H5's; the screen that asks for deletion is T-305's.
