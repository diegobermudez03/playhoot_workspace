# T-202 — PWA base

**Tier:** B (Opus · medium) · **Size:** S · **Repos:** frontend · **Milestone:** H2 · **Requires:** T-201

## Goal
Make the web app an installable PWA per D-020 and V-08: manifest, icons (placeholder assets), service worker, offline page, update notice and a non-intrusive install offer. No push of any kind (P29).

## Read first
- `DECISIONS.md` D-020, V-08; `SPEC_MAP.md` §1 (PWA row) and P01§5 in full (`docs/definitivos/md/post_01_alcance_y_alcance…` — section 5).
- `playhoot_frontend/AGENTS.md` (assets rule: register placeholders in `assets.json`, document in `docs/design/ASSETS.md`).
- T-201's Result (the framework-mode build the worker must precache).

## What to build
1. Web manifest: working name (swappable, P36§7), short_name, standalone display, start URL, theme/background colors from tokens, icon set registered as **pending assets with generated placeholders** (maskable + regular, 192/512).
2. Service worker: precache the built shell; network-first for navigations with offline fallback page; **never cache `/v1` or `/admin` API responses; never intercept WebSocket upgrades**. Cache versioning tied to the build; old caches cleaned on activate.
3. Update flow: when a new worker is waiting, show a discreet "refresh for the new version" notice; activating happens on next navigation or on accepting the notice.
4. Install offer: an "Install Playhoot" entry always available in the shell menu area (a temporary placement until T-204's shell lands is fine), plus the one-time dismissible hint per V-08 (`beforeinstallprompt` on Chromium; on iOS an instructions sheet). Never interrupts an activity (P01§5).
5. No push code, no Notification permission request anywhere.

## Acceptance criteria
- `npm run check` passes; Lighthouse (or equivalent) reports the app installable.
- With the dev/preview server stopped mid-session, navigation shows the offline page; API data is never served from cache.
- A rebuilt version produces the update notice and activates cleanly.
- Manual validation steps for Android and iOS written into the Result (the creator runs them on real devices at the H2 close).

## WCAG 2.2 AA checks (this task)
- The install hint and update notice are reachable and dismissible by keyboard, announced to screen readers (`role="status"`), and never trap focus.
- The offline page meets contrast and has a clear retry action.

## Out of scope
Final icons (creator supplies files for the pending assets), push (never), offline gameplay.

## Result

**Done 2026-11-15.** The web app is an installable PWA. Everything new lives in
`apps/web/src/pwa/`, and two files of the deployed site are written by the build rather than by
hand: `sw.js` and `offline.html` (D-026).

**Why the build writes them.** Both have to know what this build produced — the worker precaches
the exact shell files, whose names carry their content, and the offline page is one of the files
it precaches. A Vite plugin of ours (`apps/web/vite-pwa.ts`) bundles `src/pwa/sw.ts` with esbuild
as a module worker, injecting the build's identity (a hash of the worker source, the offline page
and the precache list, so an unchanged rebuild announces nothing) and the list of shell files: the
browser entry, the document, and everything they import before a route is chosen — 18 entries
including the manifest and the icons. No PWA framework was added.

**What the worker does, and what it refuses to do.** Its whole routing policy is `swPolicy.ts`,
plain TypeScript with no browser globals, unit-tested on its own. It answers a navigation from the
network and falls back to the offline page; it serves the precached shell and content-hashed files
from one cache per build; and it does not answer anything else at all. `/v1` and `/admin/v1`, a
WebSocket upgrade, anything that is not a GET and anything from another origin are passed through
untouched. Nothing is ever written to a cache but the precache list and files whose name carries
their content hash — so a backend answer, or a URL carrying a sign-in's one-time code, cannot be
stored by any path, by construction rather than by a rule someone has to remember. Activating
deletes every other `playhoot-*` cache. The host now serves `sw.js` with `no-cache`.

**The offline page.** It renders with no application and no network, so it cannot use react-intl
and cannot load a stylesheet. The build writes it from the message catalogs in all three
languages, with its few colours taken from the semantic tokens, and it picks a language in the
browser the way the server would: the `playhoot_locale` cookie (D-024), then `navigator.language`.
The retry button reloads the address that failed and takes focus. It claims nothing about playing
offline.

**Update.** A new build waits instead of taking over, so a running session is never swapped under
the people in it. A discreet card in the corner says a new version is ready, with Refresh and
Later; accepting tells the waiting worker to take over and reloads once it has. Dismissing changes
nothing — the new build still activates on the next navigation.

**Install (V-08, P01§5).** An "Install Playhoot" entry sits in the top bar whenever the browser can
install (icon only on a narrow screen, with its words in the label) — a temporary placement until
T-204 builds the shell's menu. Separately, a returning visitor is shown a one-time hint after
their second visit on a different day, which they can dismiss forever; distinct days are counted
in `localStorage`. On Apple's browsers, where no page can install anything, both show the two
lines that say how instead. Nothing interrupts an activity, and **no push code and no permission
prompt exists anywhere** (P29).

**Accessibility.** Both notices are `role="status"` cards: they announce themselves, take no focus
and trap none, cover nothing, and every action in them is a real button reachable and dismissible
by keyboard with a visible focus ring. Contrast was computed: the offline page is 16.9 (heading),
10.8 (body) and 10.4 (retry button); the notices are 12.4, 7.9 and 10.4. The quiet outlines of the
install entry and the "Later" button were moved from `--color-border-strong` (1.9:1, below the
3:1 WCAG 1.4.11 asks of a control's boundary) to `--color-text-subtle` (4.7:1).

**Verified in a real browser.** `npm run check` green (525 tests, 19 new: the worker's policy and
the hint's eligibility). Beyond that, this session drove headless Chrome over the DevTools
protocol against a production build served by `server.js`, and every one of these passed:

- the worker registers at scope `/` and activates; exactly one cache exists for the build, holding
  the offline page, the manifest, the icons and the browser entry;
- a `/v1` call leaves nothing in any cache;
- Chrome parses the manifest with no errors and **reports no installability error at all** — the
  signal Lighthouse's "installable" is made of;
- a rebuilt worker waits rather than taking over, the update notice appears with both its actions,
  and accepting it activates the new build, deletes the old cache and takes the notice away;
- with the host stopped mid-session, a navigation to an address nothing had cached shows the
  offline page, in the browser's language, with one language visible and focus on retry; the
  remembered language wins over it; a shell file is still served; and a `/v1` call fails as a
  network error instead of being answered from a cache.

**Icons.** The four app icons are **placeholders**, generated by `npm run icons`
(`scripts/make-placeholder-icons.mjs`, which draws the night square and Hoot's two amber eyes
pixel by pixel and encodes the PNG with `zlib`; there is no raster library here). They exist
because a browser refuses to offer installation without the icons the manifest names. Replacing
them is dropping four files at the same paths — nothing in the code changes. `ASSETS.md` says so,
and `CREATOR_TODO.md` P-14 asks for the real art.

**Left for the creator (CREATOR_TODO P-13), because only a real device can answer it.** On an
**Android** phone in Chrome: open the site, confirm the "Install Playhoot" entry in the top bar
and, from the second visit on another day, the hint; install from either; check it opens in its own
window with the name and icon, that rotating and the on-screen keyboard behave, and that turning
the network off during a navigation shows the offline page. On an **iPhone** in Safari: the same
entries show the "Add to Home Screen" instructions instead; follow them, then check the icon on
the home screen (opaque, not black), that it opens without Safari's chrome, and the offline page
with the network off. Report anything that differs at the H2 close (T-207).

**Not done here, by design.** Final icon art, push of any kind (never), and offline gameplay.

**Site data.** One new screen, `offline` (`implemented`, `variants: single` — it is a page of its
own, not a screen of the app). The planned `app-shell` now says T-202 built the install offer and
the update notice and placed them in the bar, and that T-204 moves the install entry into its
menu. Validator at 0 (418 entities).

**One warning left in the build output.** Vite now prints that importing a module without a file
extension is unsupported by its future native config loader — `vite-pwa.ts` reaches the message
catalogs that way, and the catalogs reach each other. It is a forward-compatibility notice, not an
error, and it applies to the repository's own import style rather than to this task; whoever
changes that style should change it everywhere at once.
