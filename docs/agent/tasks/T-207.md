### 1 · Rendering and SEO (D-019) — `scripts/verify/seo.mjs`

Nine public pages (three paths × three languages) fetched from a production build served by
`apps/web/server.js`, with no JavaScript executed. Each one carries: the right `<html lang>`, a
title and description of its own in its own language, the canonical the address names, hreflang
for `es`/`en`/`pt-BR` plus `x-default`, Open Graph (title, description, url, locale, image), and —
for the home pages — JSON-LD whose `@type`, `inLanguage` and `url` match. `robots.txt` names the
sitemap and disallows what is private; the sitemap lists exactly the six indexable addresses with
their alternates and no sign-in; `/`, `/join` and `/sign-in` redirect by `Accept-Language`
(`es-CO` → `/es…`); an address nothing answers is a 404; `/en` asked for by a Portuguese reader is
still English. **Green, 0 problems.**

**It did not start green.** `/{language}/join` — a page the sitemap offers to crawlers — answered
with its metadata and an **empty `main`**, because it sat under `ClientLayout`, which renders
nothing on the server. So did `/{language}/sign-in`. Both were settled in the direction D-032
records: the join entry is now rendered by the server, and the authentication screen stays
client-rendered on purpose, which the script encodes as a rule rather than as an exception someone
has to remember. Making the join entry server-rendered meant three small things: it picks its
skeleton with `useMediaLayout`; `useNavigateToOperation` tolerates the window before the app is
interactive by going straight to the destination, which gates itself; and `AppShell` reads from the
address that this page shows its own big logo, as it already did for the admin area, so the bar is
right on the first render instead of one frame later. One consequence, deliberate: an account with
no display name yet sees the join entry before the name gate, exactly as it already did on the home
page, and the gate still fires on `/join/{code}`.

### 2 · PWA (D-020, P01§5) — `scripts/verify/pwa.mjs`

36 checks against the final build: the worker registers at `/` and activates; exactly one cache
exists for the build and holds the offline page, the manifest and the icons; a call to `/v1` leaves
nothing in any cache; the manifest asks for its own window, names the app, declares 192, 512 and a
maskable icon and every one of them is served; **nothing has subscribed to push and no notification
permission was ever asked for** (P29); the offline page is a document of its own that loads no
stylesheet and nothing from the build it cannot reach; and, with the network really cut, a
navigation to an address nothing had cached shows the offline page, in one language, with focus on
its single retry button, while a `/v1` call fails instead of being answered from a cache. **Green.**

A note on how that last one is done, because it is the check most easily faked: the page and the
service worker have separate network stacks, so cutting only the page off leaves the worker
fetching happily and answering with the real site. The script attaches to the worker's own target
and cuts that too. Before it did, the check passed while proving nothing.

`offline` is now `verified`. **What no emulated browser can answer is still open**: installing on a
real Android phone and a real iPhone (`CREATOR_TODO.md` P-13, steps in T-202's Result). The creator
has not reported on it, so it stays open rather than being written down as done.

### 3 · WCAG 2.2 AA (P14§3) — `scripts/verify/a11y.mjs`

axe-core 4.14.1, every rule the standard calls A or AA up to 2.2, nothing switched off, on
**twelve screens**: the home page in each language, the join entry, the contextual sign-in in both
its halves, the admin sign-in, the admin second factor, and the four admin panels against a live
backend in real admin mode. **Zero violations on all twelve.** The report prints each screen's `h1`
and refuses to run if the address it reached is not the one it asked for — the admin panels are
reached by following the navigation's own links, because admin mode is a token in memory (D-031)
and reloading the page would have audited the sign-in screen four times under four panel names.
The queues panel was audited with two dead tasks present, so its table was really there.

**Three real defects, all fixed here:**

1. **No document title on any app route** (2.4.2, level A). Only public routes exported `meta`, so
   the whole admin area — and my games, the workspace, a session — served a document with no
   `<title>` at all. `root.tsx` now declares a fallback and `seo/meta.ts` gained `appMeta`; the six
   admin screens name themselves in all three languages (D-032).
2. **Every `Dialog` built its heading id from its own title text**, so an untitled dialog was
   `-title`, two dialogs sharing a title pointed at each other's heading, and `aria-labelledby`
   could resolve to the wrong element. It is `useId()` now.
3. Contrast violations that **were not real**, and the reason matters: screens arrive with an
   entrance that fades them in, and axe was measuring mid-fade — the same element reported 2.19 and
   then 1.98 on two runs. The script now waits until every animation on the page has finished. With
   that, nothing fails. This is written into the script because the next person to run an audit
   would otherwise rediscover it as six serious violations.

**What axe could not decide, looked at by hand:** a `<select>` whose dropdown arrow is drawn with a
CSS gradient — its text is ink on paper, 15:1 — and the join-code input, which is transparent
because the tiles beside it carry the characters. Both fine.

**Manual keyboard pass** on home, the join entry and both halves of the sign-in: tab order from the
top is skip link → logo → join → create → the three modes → language → sound → account → menu →
the page's own controls, in reading order; **every stop showed the ink ring** (≥ 2 px,
`:focus-visible`); **no target under 24 × 24 px** except one link inside a sentence, which 2.5.8
exempts; the walk ended by itself on every screen, so nothing traps. The mode-switch dialog is
`:modal`, labelled by its own heading, opens with focus inside it, keeps focus on its own controls
while tabbing (between the last and the first, focus rests on the document, which is Chrome's own
behaviour for `<dialog>`; it never reaches a control behind), and Escape closes it and gives focus
back to the control that opened it, with the mode unchanged.

### One trap worth knowing

After changing `apps/web/src/routes.ts`, an incremental `npm run build` can emit a server bundle
that still carries the **previous** route tree, and the symptom is a route that renders an empty
page while the dev server renders it correctly. Remove `apps/web/.react-router` and `apps/web/build`
first. It is in the frontend's `AGENTS.md` now; it cost half an hour here.
