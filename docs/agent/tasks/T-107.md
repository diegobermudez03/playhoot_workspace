# T-107 — Analytics ingestion

**Tier:** C (Sonnet · medium) · **Size:** S · **Repos:** backend · **Milestone:** H1 · **Requires:** T-101

## Goal
The new `analytics` domain, ingestion only: the event store and the queue path into it, with the first real events flowing.

## Read first
- `playhoot/docs/system/analytics.js` (table, operation) and flow `ingest-analytics-events` in `flows.js`.
- `DECISIONS.md` D-010; SPEC_MAP §20 (analytics scope); P34§2-3 only if unclear.

## Deliverables
1. `analytics_events` and `analytics.ingest-events`; the orchestrator handler for `analytics-event` tasks.
2. First emitters from what already exists: `game` enqueues `game-created` in its queue when a game is created; `play.session` enqueues `session-started` with whether real participants joined. `account_kind`/`plan_kind` are `personal`/`free` constants until H3/H6 provide real values (note it in the event constants).
3. Docs to `implemented` (table, operation, flow).

## Acceptance criteria
- Repo checks green; tests cover idempotent ingestion, batch handling, and that emitting never blocks or fails the business write (queue task in the same transaction, delivery async).
- Validator at 0.

## Out of scope
Metrics queries and admin reports (H10). Backfilling past activity.

## Result
Done 2026-11-15 (Sonnet · medium). Backend commit `T-107: add analytics ingestion: ...`.
- New domain `analytics`: table `analytics_events` (append-only, unique per source domain and key) and operation `ingest-events` (batch of up to 500; invalid events skipped and counted, valid ones stored, future dates stored as now, properties capped at 2 KB).
- Orchestrator `analyticsingestion`: handler for `analytics-event` tasks on the `game` and `play_session` queues (a task carries one event or an array; the queue's domain is the source). An unreadable or invalid event turns the task dead after the valid ones are stored. Registered in `main`; a domain that starts emitting joins that Register list.
- First emitters: `game` now has its queue (`game_queue_tasks`) and `CreateGame` enqueues `game-created` inside the creation transaction (key `game-created:<game uuid>`, so a replayed request adds nothing). `play.session` has its queue (`play_session_queue_tasks`) and `CommitStart` enqueues `session-started` in the start transaction with `real_participants` (key `session-started:<session uuid>`). Both use `personal`/`free` constants until H3/H6 (noted in `game/analytics.go` and `play/session/analytics.go`).
- `real_participants` is true when at least one participant is someone other than the creator; the specification does not define it further, so this is the inferable reading (the creator testing alone is not real use).
- Constructors changed: `gamelifecycle.New(db, queue)` and `sessionlifecycle.New(db, store, queue, max)`.
- Site data `implemented` (domain, table, operation, flow `ingest-analytics-events`); validator OK (408 entities).
- Tests: idempotent ingestion, same key from another domain, batch with invalid and in-batch duplicates, future date and oversized properties; handler tests; emitter DB tests (one event per creation, none for a replay or a rejected request, none when the start does not happen, flag on and off). `go build`, `go vet`, `go test ./...` green with the database.
- New migrations only: they apply on top, no need to recreate the local database.
