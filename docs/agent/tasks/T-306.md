# T-306 — Admin panels: markets and acceptance texts

**Tier:** C (Sonnet · medium) · **Size:** S · **Repos:** frontend · **Milestone:** H3 · **Requires:** T-302 (the texts endpoints)

## Goal
Add the two H3 panels to the admin area T-206 built: the market matrix over the H1 endpoints and
the acceptance-texts publisher over T-302's. Both follow the admin conventions exactly; nothing new
is invented here.

## Read first
- Site data: `admin-markets` and `admin-texts` (`playhoot_frontend/docs/system/screens-admin.js`),
  the endpoints they call (`GET/PUT /admin/v1/markets`, `GET/PUT /admin/v1/texts`,
  `GET /v1/compliance/texts/{kind}`).
- `DECISIONS.md` D-023, D-031 (the admin conventions), D-037; `STATE.md` note "A new admin panel
  adds…" (the checklist this task follows literally).
- `playhoot_frontend/AGENTS.md`; the existing admin panels in `apps/web/src/features/admin/` as the
  mold.

## What to build
1. **`/admin/markets`**: the matrix grouped by country (subdivision rows where they exist) and
   function — enabled, age, conditions note, actor, reason, effective date; tabs or filters for
   current / scheduled / history exactly as the endpoint answers them; the append form with
   effective date and reason; the `conditions_pending` 409 surfaced as "confirm the conditions are
   met and clear the note". Values rendered as the backend wrote them (D-031); no step-up (the
   operation is admin-level, not destructive).
2. **`/admin/texts`**: kinds × languages with version and publish date, missing pairs named
   plainly (P-23 points the creator here); the publish form with a preview of the text as served
   and the immutability warning; read/download of existing versions.
3. Feature state in `packages/features/admin`; routes inside the `AdminArea` layout; screen entries
   in `screens-admin.js` → `implemented`; titles and es/en/pt messages; navigation entries on the
   admin shell and its overview where it lists panels.

## Acceptance criteria
- `npm run check` (from PowerShell) green; validator at 0.
- In real admin mode against a live backend: read the seeded matrix, schedule a rule change with a
  reason and see it under scheduled, publish a text version and see `GET /v1/compliance/texts/…`
  serve it, re-publish a new version and see acceptances still point at the old one (the backend
  answers; the panel just shows it).

## WCAG 2.2 AA checks (this task)
- Tables with real headers and captions; the append/publish forms labeled with errors associated
  and announced; dialogs (if any) follow the admin `Dialog` pattern; keyboard-only operation of
  both panels; desktop-first single implementation still usable at 768 px (D-023).

## Out of scope
Free-limits and user/game admin panels (H10); moderation (H9); backend changes; step-up (not
required by these operations).

## Result

Done, 16 Nov 2026. Two panels, both following the T-206 mold exactly.

### What was built

- **Protocol (`packages/protocol/src/http/compliance.ts`)** — `adminMarketsPath`, `marketRuleSchema`,
  `marketsResponseSchema`, `SetMarketRuleRequest`; `adminTextsPath`, `textCatalogEntrySchema`,
  `textCatalogResponseSchema`, `PublishTextRequest`, `publishedTextResponseSchema`; `textLanguages`.
  Added beside the existing public compliance contract, since both endpoints are Compliance's own
  (`GET/PUT /admin/v1/markets`, `GET/PUT /admin/v1/texts`), the same way `admin.ts` already holds
  the other domains' admin panels.
- **`AdminClient` (`packages/communication`)** gained `markets`, `setMarketRule`, `texts`,
  `publishText` — every one of them over `/admin/v1`, so only the admin-mode token ever calls them
  (D-031).
- **`packages/features/admin`**: `marketsPanel.ts` and `textsPanel.ts`, the same shape as
  `queuesPanel.ts` (no step-up: both operations are admin-level, not destructive). Unit tests added
  to `panels.test.ts` (appending a rule and reading the matrix again; `conditions_pending` staying a
  conflict the admin must clear; publishing and reading the catalog again; `invalid` staying out of
  it).
- **`apps/web/src/features/admin/AdminMarketsRoute.tsx`** — current/scheduled/history as a
  three-way filter (`role="tablist"`) over one table with real headers and a caption; the append
  form (country, subdivision, function, enabled, min age, conditions note, effective date, reason);
  `conditions_pending` surfaced as its own warning telling the admin to clear the note.
- **`apps/web/src/features/admin/AdminTextsRoute.tsx`** — kinds × languages, the current version
  and date, how many older versions stand behind it, a missing pair named plainly; the publish form
  (kind, language, a new `TextareaField`) with a "preview as served" toggle and the immutability
  warning; reading and downloading the current version through the existing public
  `ComplianceClient` (no admin token needed for that call — the endpoint is anonymous).
- **`TextareaField`** is a new core component (`apps/web/src/ui/`), in the `/design` gallery, built
  on the shared `Field`/`Control.module.css` like `TextField` and `Select`.
- Navigation: `adminPaths.markets`/`texts`, two `AdminShell` nav entries, two routes under
  `AdminArea`, the overview's two new figures (current rules with how many are scheduled;
  published texts with how many kind-language pairs are missing).
- i18n: every new string in `es`/`en`/`pt-BR`, including plain function names
  (`admin.markets.function.*`) distinct from the whole-sentence `declaration.function.*` the
  declaration screen already had.
- Site data: `admin-markets` and `admin-texts` → `implemented`; `admin-home`'s `shows` and
  `actions` list the two new panels. **One correction to the site data** (METHOD §7's own rule):
  `admin-texts` promised that "existing versions can be read and downloaded", but
  `GET /v1/compliance/texts/{kind}` only ever serves the *current* version of a kind-language pair
  — an older, superseded version has no content left to read anywhere in this backend. The data now
  says exactly that; the panel reads and downloads the current version only, and simply lists how
  many older versions exist.

### Acceptance criteria

- `npm run check` (PowerShell): typecheck, lint, format, 623 tests, styles and asset registry all
  green. `node tools/validate-docs.mjs`: 456 entities, 0 errors.
- Walked both panels in real admin mode against the live backend (`playhoot_t303`, the scratch
  database T-205 left, still valid): signed in as a fresh local-provider account, enrolled a second
  factor (secret read from the page, codes computed with a throwaway RFC 6238 script), entered admin
  mode. `/admin/markets` showed the seeded 408-row current matrix (AR with its `conditions_pending`
  note, the full US-state and CA-province spreads); appending `CO / subscribe`, enabled, age 18,
  effective one day ahead, moved it into **Scheduled** with "Done. The backend answered recorded."
  `/admin/texts` published a new `terms`/`en` version — the preview showed exactly the typed text —
  and `curl http://localhost:8081/v1/compliance/texts/terms?language=en` answered that exact
  content at the new version; publishing again moved the version forward again and the catalog's
  "older versions" count grew, matching D-037's immutability.

### Not verified here

- That an already-recorded acceptance keeps pointing at its old version after a newer one is
  published (D-037's "recorded acceptances keep pointing at the exact version accepted") is a
  property of `compliance.AcceptanceRequest`/`RecordAcceptance` and the versions table's structure,
  untouched by this task; the panel only shows what `AdminListTexts` answers. No account in the
  scratch database had a standing acceptance to watch survive the republish.
- The QR a fresh enrollment draws was not scanned by a real phone again; T-206 already verified the
  encoder itself by reading the symbol back in a unit test, and this task enrolled a second factor
  the same way T-206's walkthrough did (secret read as text).
