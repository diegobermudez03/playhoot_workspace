# T-205 — Contextual authentication

**Tier:** B (Opus · medium) · **Size:** M · **Repos:** frontend · **Milestone:** H2 · **Requires:** T-201; T-204 helpful (shell); T-203 if available

## Goal
Replace the current `sign-in` and `sign-in-guest` screens with the single contextual authentication screen of the site data (`auth-contextual`): it receives the reason, the minimum account type that works, and returns to the operation with its data kept. B: identity flows and P14§1 govern; C-01 fixes what a guest is asked.

## Read first
- Site data: `auth-contextual` in `playhoot_frontend/docs/system/screens-shell.js`; existing `sign-in`, `sign-in-guest`, `sign-in-complete` entries.
- `SPEC_MAP.md` §5; P03 §8-§10 in full (`docs/definitivos/md/post_03_…`); P14§1; `DECISIONS.md` C-01.
- `playhoot_frontend/AGENTS.md`; the existing `feature-sign-in` package (the return-to mechanics it already has).

## What to build
1. One route (`/sign-in`) whose input (URL per path-navigation rule) carries: reason kind (translated client-side; never backend text), required level (`guest` suffices or `account` required), and the return destination with its pending data (the existing feature-state continuation mechanism; extend it rather than invent a second one).
2. Presentation: when a guest suffices, the display-name field is the primary action and account sign-in is secondary; when an account is required, Google is featured, the local development provider appears where offered, and a disabled "code by email" entry notes it arrives with H3 (visible so the layout is final; not interactive).
3. Guest-to-account warnings per P03§10: registering keeps identity and history; signing in to an existing account does not merge — warn before redirecting.
4. Callers (join, create, host flows that today navigate to `sign-in`) updated to pass reason + required level; `sign-in-complete` keeps working as the provider return.
5. Horizontal and vertical implementations; site data: `auth-contextual` → `implemented`, retire `sign-in` and `sign-in-guest` entries, validator at 0.

## Acceptance criteria
- `npm run check` passes; validator at 0.
- Walkthrough in the browser: joining without any identity asks only for a display name and lands back in the join with the code kept (C-01); creating a game without an account routes through the account-required variant and returns to creation.
- Copying the sign-in URL reproduces the same contextual screen (path defines input).

## WCAG 2.2 AA checks (this task)
- Form fields labeled, errors associated (`aria-describedby`) and announced; submit reachable by Enter.
- The reason text is a real heading; focus lands on it when the screen opens.
- Provider buttons have accessible names beyond logos; contrast per tokens; redundant entry avoided (2.2 3.3.7: returning keeps what was typed).

## Out of scope
Email-code backend and real Google verification (H3/delivery 2), account profile, linking methods (H3).

## Result

**Done 2026-11-16.** `sign-in` and `sign-in-guest` are gone; there is one screen, `/{language}/sign-in`,
whose address is its whole input (D-030).

**The address.** `reason` is a kind from a closed list (`features/paths.ts`) that the screen
translates — no caller and no backend ever supplies that text; `level` is the weakest identity that
works (`guest`, else an account); `use=account` means the person asked for the account options
although a guest would do; `next` is where to continue and still carries everything already typed.
`authPath` composes it and `authRequest` reads it back, and an address this build does not
understand reads as the strictest screen: no reason, an account required. `/sign-in/guest` and its
language redirects were removed.

**The screen.** The reason is the `h1`, and focus lands on it when the screen opens, so the first
thing read is why it appeared. When a guest suffices, the display-name field is the main action
(C-01: a name and nothing else) with the account options one link below; when an account is
required, Google is featured, a disabled "code by email" entry holds its place (its endpoint
arrives with H3) and the fictitious local provider appears only where the backend offers it. Both
halves are the same route, so the name typed survives the move between them. A guest who chooses an
account is warned in a `Dialog`, before the app is left for the provider, that a new account keeps
their name and games while entering an existing account does not merge them (P03§10) — it is a
confirmation, not a paragraph, because that is the moment the consequence becomes real.

**The callers.** `RequireOperation` and `useNavigateToOperation` now take the reason beside the
operation; the backend's catalog still decides the level. Join, create a session, the host screen,
create a game, the workspace, my games and the AI connection screens each name their own reason.
`sign-in-complete` is untouched and still returns the person where the sign-in started.

**Verified in the browser** (Chrome over the DevTools protocol, against a live backend):

- Joining with no identity shows the guest half with the code kept in `next`, focus on the heading,
  the field labelled and its hint wired through `aria-describedby`; Enter submits, and the person
  lands back in `/join/ABC234` with the code still there (the Session does not exist, so the join
  says so — which is the join's own answer, not this screen's).
- Creating a game without an account shows the account half, and the whole provider round trip ends
  at `/games/new`.
- As a guest, choosing an account opens the warning with the guest's name, focus inside the dialog;
  with nobody signed in there is no warning and the provider is reached directly.
- A copied address reproduces the same screen on a cold load, in the language the address names; the
  link between the two halves keeps the reason, the level and the destination.
- 320, 390 and 1280 px: no horizontal scrolling, one column below 600 px and the split skeleton
  above it.

**The backend gap was misdiagnosed.** `logo_image_url` exists in no migration and nowhere in the
backend source: it survives only in the creator's local database, from a migration edited in place
before launch. A database created now migrates, seeds and serves without a code change, which is
what this walkthrough ran against. `GAPS.md` is corrected and the one-off recreation is
`CREATOR_TODO.md` P-16.

**Site data:** `auth-contextual` → `implemented` with its address and behaviour; the `sign-in` and
`sign-in-guest` entries are retired and the top bar now points at `auth-contextual`. Validator: 415
entities, 0 errors. `npm run check`: green.
