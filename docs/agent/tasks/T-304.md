# T-304 — Frontend: the ways in and the declaration

**Tier:** B (Opus · medium) · **Size:** M · **Repos:** frontend · **Milestone:** H3 · **Requires:** T-301, T-302 (their endpoints live)

## Goal
Make the contextual sign-in screen complete — the email-code way in live, the acceptance step, the
guest-expiry disclosure — and build the contextual declaration screen that gated operations send
people to. D-030 stays the shape; D-033, D-037 and D-038 say what changes.

## Read first
- Site data: the changed `auth-contextual` and `sign-in-complete`, and the new `declaration` screen
  (`playhoot_frontend/docs/system/screens-shell.js`, `screens-identity.js`, `screens-account.js`).
- `DECISIONS.md` D-030 (the pattern), D-033, D-037, D-038, V-09; P03§8,§10; P19§1-3; C-01.
- `playhoot_frontend/AGENTS.md`; the sign-in feature state T-205 built (reason/level/next and the
  pending-login store — extend them, never a second mechanism).

## What to build
1. **Email code on `auth-contextual`**: the address field beside Google, the "we sent a code" state
   with the 6-digit input (screen state, not the address — the attempt lives on the server, like
   the provider trip), start/complete calls, the same neutral wording whatever the address, the
   V-09 error kinds (wrong, expired, superseded, exhausted → offer a new code), and the guest
   warning of P03§10 also before a code is sent. The guest half gains the one-line 90-day
   disclosure (P02§9).
2. **The acceptance step (D-037)**: after a sign-in completes, if the account lacks a standing
   acceptance of the current terms or own-data text (the texts endpoint answers it), one step names
   both with links and records each at its exact version before continuing to `next`. Guests never
   see it; the footer links the texts.
3. **The declaration screen (D-038)**: `/declaration?function={kind}&next={path}` per its site
   entry — the address is the input, the function kinds are a closed translated list beside
   `authReasons`, country then subdivision only where needed, the declaration checkbox worded with
   the threshold the backend answers, `conflict` explained as "corrections go through support".
   `RequireOperation`/`useNavigateToOperation` (or the operation's error path) learn to read
   `declaration_required` and route here the way they route to sign-in.
4. **`sign-in-complete`** finishes a provider link trip (pending intent in the existing store) and
   lands on the methods screen (built in T-305; the route exists by then or lands on `/profile`).
5. New messages in es/en/pt in parity; screens named with `appMeta`; site data → `implemented`;
   validator at 0.

## Acceptance criteria
- `npm run check` (from PowerShell) green; validator at 0.
- Browser walkthrough against a live backend: register with only an email, sign in again the same
  way, a guest upgrades by code and keeps name and games, the acceptance step appears once for a
  new account and not again, create-game as a fresh account routes through the declaration and
  returns with everything kept.
- Copied addresses reproduce both screens (D-030 pattern).

## WCAG 2.2 AA checks (this task)
- The code input: one labeled field (or group with a single accessible name), errors announced via
  `aria-describedby`, no paste blocking, Enter submits.
- The acceptance step and the declaration are real headings that receive focus; links to texts have
  names that say which text.
- Returning to `next` re-asks nothing (3.3.7); the declaration's subdivision select is labeled and
  keyboard-operable; all states at 320 px without horizontal scroll.

## Out of scope
Profile area and notifications pages (T-305); admin panels (T-306); backend changes.

## Result

**Done, 16 Nov 2026.** Frontend only; the backend was not touched and no migration changed, so no
local database has to be recreated (`playhoot_t303` still matches). `npm run check` green from
PowerShell, documentation validator at 0 (456 entities).

### What was built
- **The email-code way in is live on `auth-contextual`.** `packages/features/sign-in/emailSignIn.ts`
  holds the two steps as screen state (the attempt lives on the backend, like the provider trip):
  the address, then the 6 digits in the existing `CodeInput`, with a new code and a change of
  address beside it. The acknowledgement is the same words whatever the address; the error kinds
  are `invalid-address`, `wrong-code`, `attempt-gone`, `rate-limited` and `unavailable`. V-09's
  four cases collapse onto the two the backend tells apart: a wrong code leaves the attempt live,
  and an expired, superseded or spent one answers `attempt_gone` and offers a new code. A guest
  meets the P03§10 confirmation before a code is sent, the same dialog as before a provider trip,
  and the guest half now states the 90-day expiry (P02§9).
- **The acceptance step (D-037), built as a gate.** `AcceptanceGate` sits in `ClientLayout` beside
  the display-name gate, so it is met once however the sign-in finished — on this screen or on the
  provider callback — and again when a version changes. It names the terms and own-data texts,
  opens each to be read at the version shown, and records one acceptance per kind at that exact
  version. Guests never meet it. The screen's footer links both texts for everyone through
  `TextLinks`, read in place with a download. Why it is a gate and not a step of the screen, and
  why an unreadable text is not asked for: D-042.
- **The declaration screen (D-038).** `/declaration?function={kind}&next={path}`, its address its
  whole input: the function as a translated kind, the country (named by the browser in the reading
  language), the state or province where it is needed, and the single declaration. Continuing needs
  the box; "I haven't reached that age" is its own confirmed action, because that answer is binding
  and corrected only through support. `conflict` says so in those words. Done, it returns to `next`
  with everything typed still there.
- **The gates route to it.** `createGame` maps `declaration_required` / `market_restricted`, and
  `/games/new` now carries what was typed in its address so the trip costs nothing; the join
  rejection reasons gained the same two, with a "tell us where you live" action that comes back to
  the same join address.
- **`sign-in-complete` finishes a link trip.** `PendingLogin` gained an intent, and
  `accountSignIn.complete` answers which trip it was, linking through
  `POST /v1/identity/me/methods/provider/complete` and landing on the methods screen with the
  outcome in the address. The methods screen itself is T-305's; nothing here starts a link yet.
- New: `@playhoot/feature-compliance` (acceptance step and declaration form, with tests), the
  compliance HTTP client, the `compliance.ts` and `emailLogin.ts` protocol modules, a `Checkbox`
  core component and an error/hint on `CodeInput` — both in the `/design` gallery. 73 new message
  ids in es/en/pt-BR parity; `auth.emailCode*` ("coming soon") removed.

### Verification
A browser walkthrough against a live backend (Chrome over the DevTools protocol, the repository's
own driver) covers, in order: the texts linked on the sign-in screen; registering with nothing but
an email and its neutral acknowledgement; the display-name gate then the acceptance step naming
both texts with their versions, and the two acceptance rows it writes; create-game refused into the
declaration with the function and what was typed in the address; the declaration recorded and the
return with the name intact; the operation then going ahead; signing in again entering the same
account and asking nothing twice; a guest warned, upgraded by code, keeping their identity and
name; a wrong code announced on the field through `aria-describedby` with the attempt still live;
five wrong codes spending it and a new code working; and both screens reproduced from a copied
address at 320 px with no sideways scroll. The code itself only exists in the email, and the local
email provider stores no body, so the walkthrough recovers it from the stored SHA-256 — worth
knowing for every later session that has to drive this path by hand.

Also corrected on the way: T-300 left three `docs/system` data files unformatted, which had
`npm run check` failing at HEAD before this task; they are formatted now.

### What this task deliberately left
- The age a place asks for is not named before the declaration is answered, and which countries
  need a state or province is a closed list in the screen. Nothing public tells a client either.
  Recorded in `GAPS.md` and D-042; H4 is the milestone that will need the same read.
- `declaration_required` and `market_restricted` are not in the telemetry error catalog (it is the
  backend's closed list, and a market decision is not a failure).
- `verify:a11y` still audits the H2 screens only; T-307 adds the H3 ones, as its brief says.
