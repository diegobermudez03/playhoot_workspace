# T-300 — H3 design: identity and access

**Tier:** A (Fable · high) · **Size:** L · **Repos:** workspace, backend, frontend · **Milestone:** H3 · **Requires:** H1 and H2 closed

## Goal
Design everything H3 builds, and only design it: the ways in that do not exist yet (one-time code
by email), the declaration of age and country and what follows from it, guests that expire, linking
methods and recovery, the profile and the account, the three modes as real identities, account
deletion, and the public entry those screens hang off. Write the design as `planned` documentation
data — domains, operations, flows, endpoints and screens with their calls — and write the
implementation tasks T-301… with the H3 board in `PLAN.md`. Write no application code.

This is the same shape of task as T-200, which designed H2; read its Result for what "design as
site data" turned out to mean in practice, and what it deliberately left out.

## What is known to be missing (from `GAPS.md`, not a complete list)
- **One-time code by email** (P03§8): the only way in besides Google. The authentication screen
  already draws its button, disabled, waiting for this endpoint (T-205).
- **Declared age and country** (P19, P35§3): `compliance` has the matrix, the declarations and the
  acceptances since T-103, but no flow asks for them. H3 wires the entry.
- **Guests expiring at 90 days** (P03 / `GAPS.md`): today they do not expire.
- **Linking methods, recovery, the profile** (P03§11-12): none of it exists.
- **The three modes** (P03§9): today there are only the levels anonymous < guest < account. The
  shell's switch explains that teacher and student are coming and leaves the person where they are;
  H3 makes normal and teacher real identities of the same account, and H8 builds what teaching is.
  **The student identity is H8's**, not this milestone's: decide here only what identity owes it.
- **Account deletion** (P02§9-11): there is none.
- **Name-change limit** (P03): there is history but no limit.

## Result
Done 2026-11-16, one session (Fable · high).

1. **Decisions D-033…D-038 + V-09…V-12.** Email-code sign-in with identity-owned attempts riding
   the existing notification path — the attempt itself is the recipient `read-contact` resolves, so
   a code reaches a person who has no user row yet and notifications never stores an address
   (D-033). Modes as identity state: `mode` on the account, carried by the token, switch
   identity-only; the planned `switch-mode` flow is retired because P15§5 forbids entitlements
   riding a token anyway; what identity owes the H8 student identity is written down so this design
   is not reopened (D-034). Linking by proving both sides, `method_in_use` instead of any merge, and
   email-code sign-in *as* the recovery of P03§12 (D-035). One deletion pipeline — synchronous
   access withdrawal, queued idempotent cleanup over game, play.session and notifications, neutral
   distinguishable reference, compliance evidence kept restricted, analytics left unlinkable — with
   guest expiry as the same pipeline on a daily timer (D-036). Terms and own-data recorded at
   registration on the sign-in screen, marketing recorded from the preferences toggle, texts
   publishable from admin (D-037). Gated flows answer `declaration_required` and the contextual
   `/declaration` screen mirrors D-030; H3 wires the two entries that exist, create-game and the
   join admission (D-038).

2. **Planned site data loaded, validator at 0 (455 entities, +40).** Backend: 2 tables
   (`identity_email_codes` + events) and 4 columns on existing identity tables; 10 new identity
   operations plus rule updates on `refresh`, `set-display-name` and `read-contact`; 3 compliance
   operations (`read-declaration`, texts admin); one cleanup operation each in game, play.session
   and notifications; 14 endpoints; flows `email-code-sign-in`, `delete-account`, `expire-guests`,
   `my-data` and `join-session` detailed with steps, the market gate added to `create-game`, and
   `switch-mode` removed. Frontend: `screens-account.js` with 8 screens (profile ×4, declaration,
   teacher, notifications ×2), 2 admin panels (`admin-markets`, `admin-texts` — the panels T-200
   deferred here), and the planned changes to `app-shell`, `home`, `auth-contextual` and
   `sign-in-complete`.

3. **Tasks T-301…T-307 written and the H3 board in `PLAN.md`**: T-301 ways in → T-302 modes,
   profile data and entry gates → T-303 deletion and expiry → T-304 sign-in frontend → T-305
   profile area → T-306 admin panels (C-tier) → T-307 close. Every frontend brief lists its WCAG
   2.2 AA checks. 8 sessions total against the 7–9 estimate.

4. **GAPS "Identity and access" rewritten**: every row designed here or explicitly assigned (student
   identity H8, AI link/OAuth reconciliation H7, real Google delivery 2, backups and privacy
   requests H11); the stale "no administrator" row corrected (built in H1).

Scope notes, deliberate: no notifications-page redesign beyond the H3 pages the emails already need;
no acceptance texts written (only the creator can, P-23 — but T-306 gives them the panel); the
teacher screen is a presentation because plans are H6 and teaching is H8 (D-029 honesty rule); the
`sign-in` screen's email-code step is screen state, not an address, because the attempt lives on the
server exactly like the provider trip.
